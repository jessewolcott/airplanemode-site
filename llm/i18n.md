# Translations (i18n)

The homepage is in seven languages. English stays at `/` (`index.html`) and is the
**source of truth**: a plain, hand-edited page. The others are generated:

| Language | URL / folder | `<html lang>` / hreflang | Own name |
|---|---|---|---|
| English | `/` | `en` | English |
| Spanish | `/es/` | `es` | Español |
| French | `/fr/` | `fr` | Français |
| Italian | `/it/` | `it` | Italiano |
| Simplified Chinese | `/zh/` | `zh-Hans` | 中文 |
| Japanese | `/ja/` | `ja` | 日本語 |
| Vietnamese | `/vi/` | `vi` | Tiếng Việt |

The list lives in `LANGS` at the top of `tools/build_i18n.py`. Every page has a canonical
link to itself, `hreflang` alternates for all seven plus `x-default` (-> `/`), and `og:url`.

## Changing the homepage (the required steps)

1. Change English `index.html`.
2. `python tools/build_i18n.py --sync-keys`: rewrites each `i18n/<lang>.json` in page order,
   new English strings as `null`, removed ones dropped (it prints both).
3. Translate every `null` in all six files.
4. `python tools/build_i18n.py`: writes `<lang>/index.html`. It refuses (and lists what's
   missing) while any string is untranslated.
5. `python tools/check_i18n.py`. CI runs it on every push (job `i18n`); the Pages deploy
   waits for it.

Never edit `<lang>/index.html` by hand: the check compares each one with a fresh render.

## How the generator works (`tools/build_i18n.py`, stdlib only)

It parses English `index.html` into a tree with source offsets (`html.parser`; the page must
be well-formed: every non-void element closed) and finds **units**, in page order:

- an element with text of its own whose descendants are all inline (`a b strong em i span
  small code kbd br input img abbr sub sup label`): its whole inner HTML is one unit, e.g.
  `Open <a href="...">FriendlyElec's download page</a> → <code>01_Official images</code> ...`.
  So a translation can reorder words around the inline elements, but must keep the same
  elements (with the same attributes) in the same order;
- the attributes `alt`, `aria-label`, `placeholder`, `title`, and the `content` of the
  description / `og:description` / `og:title` metas;
- each value of the JSON in `<script type="application/json" id="ui-strings">`: the strings
  `assets/site.js` writes (device labels, "{n} of {total} done", Copy/Copied, the "What it
  does" list). Placeholders `{n}`, `{dir}`... must survive translation.

Skipped: `<pre> <code> <kbd> <script> <style> <svg>`, anything under `translate="no"` (the
language list), `#lang-now`, and text that is only names and commands from
`i18n/allowlist.json` (`names`: AirplaneMode, Docker, LuCI menu paths, app names...) plus
URLs. Those stay byte-identical on every page.

`i18n/<lang>.json` maps the unit's English text (whitespace collapsed) to the translation.
Keys being the English text means a changed English sentence shows up as a missing key
plus a stale one, so a translation can't silently go out of date. The same English string
(e.g. "Copy" in the HTML and in `ui-strings`) has one entry.

Per page the generator also sets `<html lang>`, the canonical and `og:url`, the switcher's
current name (`#lang-now`), rewrites the `ui-strings` JSON, and prefixes relative `href`/`src`
with `../` (`assets/...`, `install.sh`, the other languages). Output is LF (`.gitattributes`
forces LF for html/css/js/json/py so the comparison is byte-exact on Windows too).

## Shared CSS and JS

`assets/site.css` and `assets/site.js` serve all pages (no copies). The JS reads its strings
from the page's own `#ui-strings`, so they always match `document.documentElement.lang`. It
finds the site root as the folder above its own `src`, which keeps the install command at
`https://airplanemode.xin/install.sh` from `/ja/` too. localStorage (`am.device`, `am.opts`,
`am.done`) is shared by all languages on purpose: step ids and options are identical, so
your progress follows you when you switch.

CJK: `:lang(ja)` and `:lang(zh-Hans)` get their own `--sans` stacks (Hiragino / Yu Gothic /
Meiryo / Noto Sans JP; PingFang SC / Microsoft YaHei / Noto Sans SC) after the Latin system
fonts, no negative letter-spacing on headings, taller lines, `line-break: strict`, and
`word-break: auto-phrase` for Japanese (Chrome breaks between phrases; others ignore it).
Translations use full-width punctuation (、。：（）「」“”). French uses a no-break space
before `:` and `»`, and a narrow one before `; ! ?` and in `10 000`.

## Language switcher and hint

`<details class="langs">` in the header (works without JS): a globe, the page's language in
its own name, and a list of all seven (`translate="no"`, identical on every page). The script
marks the current one `aria-current`, closes the menu on outside click / Escape, carries the
`#section` hash to the other language, and stores `am.lang` when the visitor picks one.

No redirect by browser language. If `navigator.languages` prefers another language we have
(Traditional Chinese `zh-TW/HK/MO/Hant` is not matched to `zh-Hans`), and the visitor hasn't
picked a language (`am.lang`) or closed the hint (`am.langHint`), `#lang-hint` shows that
language's `data-hint` sentence (from the switcher link, in that language) as a link, with a
close button.

## The check (`tools/check_i18n.py`), per language

- `i18n/<lang>.json` has exactly the English keys, none empty, placeholders kept;
- `<lang>/index.html` equals a fresh render (first differing line reported);
- same elements in the same order: tag, id, class, href/src (resolved against each page's
  URL), `data-*` and all other attributes except the translated ones; plus explicit counts
  of app cards, setup steps, sections and images;
- `<code> <pre> <kbd> <script> <style>` and `translate="no"` text byte-identical (the install
  command, paths, the language list);
- `<html lang>`, canonical, `og:url`, `#lang-now`, and the hreflang set on every page
  (English included), and switcher links to all seven pages;
- no leftover English: a text node, translated attribute or `ui-strings` value identical to
  English that still has words after removing allowlisted names, commands and URLs. Strings
  whose right translation equals English go in `same.<lang>` in `i18n/allowlist.json`
  (today only Spanish "Apps").

Messages name the language and the element path (`[ja] li > div.step-body > p > code:
...`). With `../airplanemode/portal/apps.json` present (or `--apps PATH`) it also checks
that the English app cards match the platform's apps.json (name, description, category,
"uses the model" exactly when `uses_llm`). CI does that against the platform's live `main`
as a warning-only step, since the platform can change first.

## App cards

There is no script that generates them: the cards in English `index.html` are copied by hand
from the platform's `portal/apps.json` (the check above catches drift); their descriptions
and tags are translated like any other text.

## What stays English on purpose

Product and app names, hardware models, OpenWrt/Docker/LuCI, commands and paths, IPs and
URLs, and the LuCI / GL.iNet / AirplaneMode admin menu labels in bold (`System →
Administration`, `Network → Wireless`, `Applications → Network Storage`, `Internet source`):
the visitor has to find those exact words in UIs that are English (the AirplaneMode admin
panel is English-only). The screenshots are the English UI.
